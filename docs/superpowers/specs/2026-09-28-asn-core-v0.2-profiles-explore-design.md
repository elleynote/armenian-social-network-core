# ASN Core v0.2 — Profiles and Explore Design Specification

**Date:** 2026-09-28  
**Repository:** `elleynote/armenian-social-network-core`  
**Project:** Armenian Social Network rebuild  
**Milestone:** ASN Core v0.2.0  
**Status:** Design approved for implementation planning

## 1. Goal

Build the first member-facing ASN Core modules: **Profiles** and **Explore**.

The purpose of v0.2 is to prove that ASN Core can read, display, search, filter, and safely edit the site's existing WordPress member data without depending on the legacy TunApp social shortcodes for those features.

The current live Profile and Explore pages stay untouched while the new modules are built and tested on separate test pages. Cutover happens only after the new modules are functionally complete and verified against the current site.

## 2. Scope

ASN Core v0.2 will add:

- a Profiles module
- an Explore/member-directory module
- a normalized searchable profile index backed by the existing `asn_profiles` table
- profile viewing for existing WordPress users
- edit-own-profile behavior for approved existing fields
- server-rendered Explore search and filters
- responsive member cards
- pagination
- direct profile navigation
- a transport-neutral messaging entry point that can keep using AtomChat during this phase
- test-only shortcodes/pages so the current live pages are not replaced during development
- release ZIP tooling that consistently produces WordPress-safe archives on Windows

ASN Core v0.2 will not:

- replace registration
- replace login
- replace Feed
- change billing, checkout, subscription records, or prices
- disable AtomChat
- change Tun SSO / miniOrange
- migrate users into a second identity system
- expose member email, password hashes, billing data, admin-only data, API credentials, or auth secrets
- add Better Messages yet
- add connections, profile-view tracking, extra gallery photos, or moderation workflows yet

## 3. Source of Truth

WordPress remains authoritative for member identity and profile data.

### Identity
The WordPress user ID remains the only member identity key.

### Existing profile data
Approved member fields continue to live in WordPress user data/user meta.

### ASN profile index
The `asn_profiles` table is a **rebuildable search/index layer**, not a second user database.

It may store normalized copies of searchable fields such as:

- `user_id`
- display/search name
- country
- age
- gender
- job title
- dialect/language grouping derived from proficiency
- spoken proficiency
- profile-completeness/search visibility flags
- indexed timestamps

If the index is lost or stale, it must be rebuildable from WordPress users and user meta.

Profile editing writes to the original WordPress fields first, then refreshes the ASN index for that member.

## 5. Profile Photo Handling

The new profile module must preserve the member's current visible profile image behavior.

Before implementation, the current legacy profile-photo source must be verified from the active TunApp code so ASN Core does not guess at a meta key or silently switch members to a different image source.

The Profiles module will expose a single profile-photo resolver. Its fallback order must be explicit and privacy-safe, for example:

1. verified existing ASN/TunApp profile image source
2. existing WordPress avatar source
3. plugin-provided neutral placeholder

No image migration occurs in v0.2.

## 6. Profiles Module

Planned structure:

```
modules/profiles/
├── class-asn-profile-service.php
├── class-asn-profile-shortcode.php
├── class-asn-profile-form.php
└── views/
    ├── profile.php
    └── profile-edit.php
```

Exact filenames may vary during planning, but responsibilities stay separated.

### 6.1 Profile service

The profile service owns:

- fetching a public member profile by WordPress user ID
- filtering private fields
- resolving display name
- resolving profile photo
- returning approved prompt/profile fields
- determining whether the viewer owns the profile
- updating approved own-profile fields
- refreshing that member's search index

It must never expose:

- `user_email`
- `user_pass`
- login names unless explicitly approved later
- billing addresses
- payment/subscription details
- admin capabilities
- API/token/secret values

### 6.2 Public profile route behavior

The new shortcode will be:

```
[asn_profile]
```

Behavior:

- if a valid member query parameter is present, show that member
- otherwise, for a logged-in user, default to the current user's profile
- nonexistent/invalid users render a controlled "Member not found" state
- logged-out access follows the existing site access policy; v0.2 does not invent a new membership gate
- profile output is server-rendered and does not require JavaScript to display core content

The preferred query parameter is:

```
?member=<wordpress_user_id>
```

Explore links use the same parameter so the eventual live cutover does not require a second profile routing system.

### 6.3 Edit-own-profile

Only the logged-in owner may edit their profile.

State-changing requests require:

- logged-in user check
- ownership check
- WordPress nonce verification
- field allowlist
- field-specific sanitization
- safe redirect/message after save

Initial editable fields:

- first name
- last name
- country
- age
- gender
- job title
- spoken proficiency
- approved profile-card prompt fields

The editor must not allow users to submit arbitrary meta keys.

### 6.4 Field validation

Examples:

- age: bounded integer, not arbitrary text
- country: sanitized short text
- gender: allowlisted values matching current site behavior
- spoken proficiency: allowlisted values matching current site options
- prompt fields: sanitized textarea content with sensible length limits
- names/job title: sanitized short text

Exact current select values must be read from the existing site configuration before implementation rather than guessed.

## 7. Explore Module

Planned structure:

```
modules/directory/
├── class-asn-directory-service.php
├── class-asn-directory-shortcode.php
├── class-asn-directory-query.php
└── views/
    ├── directory.php
    └── member-card.php
```

The new shortcode will be:

```
[asn_explore]
```

### 7.1 Directory behavior

Explore will query the ASN profile index and join back to WordPress identity only as needed.

Initial functionality:

- newest/available members listing
- text search
- dialect filter
- proficiency filter
- country filter
- pagination
- responsive cards
- direct profile link
- messaging entry point
- empty-results state

The first version should use standard server-rendered GET requests rather than requiring an AJAX framework.

Example:

```
/asn-explore-test/?q=anna&dialect=western&proficiency=advanced&country=Australia&page=2
```

This keeps the feature accessible, easy to debug, and easy to cache correctly at the query/data layer without full-page caching authenticated member content.

### 7.2 Existing filter behavior to preserve

The current Explore page already supports:

- dialect filtering
- proficiency filtering
- combined filters
- newest-first behavior
- incremental member loading

v0.2 must preserve the useful behavior while moving the data source away from AtomChat's user-list dependency.

The initial proficiency model must support the site's current distinctions, including Beginner, Intermediate, Advanced, and Fluent/Fluent Speaker terminology as configured on the current site.

### 7.3 Pagination

For approximately hundreds of current users, use indexed SQL pagination with a conservative page size.

Default target:

- 20 members per page

Do not load all members into PHP and filter in memory.

### 7.4 Search

Search should target approved searchable fields only, such as:

- display/member name
- country
- job title

Search must not include email or private account information.

## 8. Profile Index Synchronization

The `asn_profiles` table must stay rebuildable and synchronized.

### 8.1 On-demand sync

When a profile is edited through ASN Core:

1. validate and write approved WordPress user meta
2. rebuild that member's `asn_profiles` row
3. confirm success
4. return the user to the profile with a controlled status message

### 8.2 Existing-member backfill

The current site's existing users need index rows before the new Explore module is tested broadly.

Backfill must:

- run in batches
- be resumable/idempotent
- never change the source WordPress member data
- skip/record users that cannot be indexed cleanly
- avoid long single-request loops across all users
- expose progress/status only to administrators

For the current site size, a small batch-based admin action is sufficient; a complex queue system is not required for v0.2.

## 9. Membership Rules

PMPro remains the entitlement layer.

v0.2 must use the existing `Memberships` helper instead of calling PMPro directly from templates.

Basic Profile and Explore functionality should preserve the site's current access behavior.

Premium-only filters or premium profile features are not expanded in this milestone unless they already exist and are required for parity.

No subscription or payment record is modified by Profiles or Explore.

## 10. Messaging Entry Point

AtomChat remains live during v0.2.

Explore/member profile UI may expose a "Message" or "Say hello" action, but the UI must not hardcode AtomChat-specific business logic throughout the Profiles or Directory modules.

Introduce a small messaging-action abstraction whose responsibility is only:

- determine whether messaging is available
- produce the current member-to-member message action/target
- return a controlled unavailable state if the current transport is unavailable

The current implementation may delegate to AtomChat. A later Better Messages phase can replace the adapter without rewriting member cards or profiles.

## 11. Front-End Design

ASN Core front-end markup and styles must be independent of Astra/WPBakery internals.

Rules:

- use `asn-` prefixed CSS classes
- no global element selectors that can alter the existing site
- mobile-first responsive layout
- semantic HTML
- keyboard-accessible controls
- labels for form fields
- visible focus states
- no dependency on theme JavaScript
- no inline secrets or private data in HTML attributes

The design should visually fit the existing Armenian Social Network branding without requiring a theme child-template override.

## 12. Test Pages and Safe Cutover

The current live pages remain unchanged during development.

Create the shortcodes:

- `[asn_profile]`
- `[asn_explore]`

Testing is done on separate unlinked/private test pages, for example:

- `/asn-profile-test/`
- `/asn-explore-test/`

The plugin must not automatically overwrite the live Profile or Explore pages.

### Cutover gate

Only after parity testing:

1. verify new profile display
2. verify own-profile editing
3. verify Explore search/filters/pagination
4. verify message entry point
5. verify PMPro access behavior
6. verify mobile layouts
7. verify no private data exposure
8. verify legacy Profile/Explore still work while new pages are tested

Then the existing live pages may be manually switched from:

- `[tac_user_profile]` → `[asn_profile]`
- `[tac_contacts]` → `[asn_explore]`

The legacy plugin remains installed until later phases because registration and Feed still depend on it.

## 13. Error Handling

Profiles and Explore must fail safely.

Examples:

- nonexistent member → controlled "Member not found"
- stale/missing ASN index row → rebuild or fallback path, not fatal
- PMPro unavailable → existing defensive integration behavior
- AtomChat unavailable → profile/directory still render; message action disabled
- failed profile update → no partial arbitrary-meta writes; show controlled error
- failed index refresh after source profile save → log/admin-visible warning and preserve the saved WordPress source data

No raw database errors, stack traces, secrets, or file paths are shown to normal users.

## 14. Security

All v0.2 state-changing actions must include:

- authentication
- authorization/ownership
- nonce validation
- allowlisted fields
- sanitization
- escaped output

Directory/profile reads must enforce a public-field allowlist.

SQL must use WordPress prepared statements or safe `$wpdb` APIs.

No query parameter may be used directly in SQL.

## 15. Performance

Target behavior for the current site:

- directory queries use indexed `asn_profiles` columns
- 20 members per page by default
- no full-site user scans on ordinary Explore requests
- no dependency on AtomChat's user listing for directory data
- profile pages perform a bounded number of WordPress/meta reads
- member cards use appropriately sized/lazy-loaded images
- authenticated Profile/Explore pages remain dynamic and must not be served from inappropriate full-page cache

## 16. Release and Deployment Workflow

GitHub remains the canonical source.

During development:

- work on `develop`
- CI must pass before a release build
- keep secrets out of the repository
- the repository may remain public during active development only if no sensitive material is committed

For deployment, use versioned manual WordPress plugin ZIPs rather than WP Pusher/Git Updater for now.

Add a repeatable release build script that:

- creates one top-level `asn-core/` directory
- uses forward-slash ZIP entry paths so Linux WordPress installs correctly
- includes runtime plugin files only
- excludes Git metadata, tests, local build output, and development-only files
- names the archive using the plugin version, such as `asn-core-v0.2.0.zip`

A versioned ZIP is uploaded through WordPress Admin and replaces the existing ASN Core plugin.

## 17. Testing Requirements

Automated tests must cover at minimum:

### Profiles
- valid member read
- nonexistent member
- private fields excluded
- owner detection
- unauthorized edit denied
- invalid nonce denied
- arbitrary meta key rejected
- field sanitization
- valid own-profile update
- index refresh after update

### Directory
- search query behavior
- dialect filter
- proficiency filter
- country filter
- combined filters
- pagination
- private fields never included
- missing/stale index handling

### Indexing
- single member sync
- batch sync idempotency
- source user meta remains unchanged
- failed sync is reported safely

### Integrations
- PMPro missing
- AtomChat/messaging transport missing
- profile/directory still render without optional transport

### Regression
- legacy `[tac_user_profile]` and `[tac_contacts]` remain untouched until manual cutover
- Feed, registration, login, billing, AtomChat, and Tun SSO remain unchanged

## 18. Versioning

Release target:

```
ASN Core 0.2.0
```

The plugin header, `ASN_CORE_VERSION`, changelog, tests, and release ZIP filename must agree on the same version.

## 19. Definition of Success

v0.2 is successful when:

- existing WordPress members appear correctly in the new profile view
- users can safely edit only their own approved profile fields
- the new Explore directory no longer depends on AtomChat to discover members
- search and basic filters work on indexed ASN profile data
- member cards link reliably to the new profile view
- current AtomChat messaging remains usable through a replaceable entry point
- no private account/billing data is exposed
- the current live Profile/Explore pages can remain untouched until final cutover
- the release can be packaged repeatedly into a valid WordPress ZIP and upgraded manually
- Feed, registration, login, billing, AtomChat, and Tun SSO continue working as before
